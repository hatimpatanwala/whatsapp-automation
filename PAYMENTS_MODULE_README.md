# PAYMENTS MODULE — Build Brief & README

**Product:** WhatsApp Business Automation Suite (ERP + SFA + E-Commerce)
**Module:** Payments & Collections
**Status:** Design brief for implementation
**Audience:** Future Claude instances / developers picking up this module

---

## 0. How to read this document

This is both a **master prompt** (a complete, unambiguous description of what to build) and a **README** (reference for how the module behaves once built). If you are implementing this, read Sections 1–4 for intent, Sections 5–10 for the technical spec, and Section 11 for open decisions the product owner still needs to make.

The design principle throughout: **make it cheap for the merchant to start collecting money, and make it painless to upgrade to automated collection when they grow.** Every rupee of transaction fee and every minute of manual reconciliation is friction we are trying to remove.

---

## 1. Scope & product intent

The Payments module lets a merchant (our client, or their sub-clients) collect money from *their* customers. It must work in three provisioning states, sold as tiers:

| Mode | What it is | Who enables it | Cost to merchant | Confirmation |
|------|-----------|----------------|------------------|--------------|
| **A — Manual collection** | Admin uploads static QR / UPI ID / bank details. Customer pays. Admin manually confirms receipt. | On by default for every merchant | ₹0 (no MDR — money hits their bank directly) | Manual — admin clicks **"Payment Received"** |
| **B — Auto-reconciled UPI** *(recommended addition)* | System issues a **unique virtual UPI ID / virtual account per invoice or per customer**. Payment auto-matches to the invoice via webhook. No admin click needed. | Enabled by us on request; needs a collection account (e.g. RazorpayX / Cashfree) | 0% on UPI up to ₹2,000/txn (banks bear MDR per RBI) | **Automatic** |
| **C — Full payment gateway** | Standard checkout: UPI + cards + net banking + wallets + EMI/BNPL, in-app or via link. | Enabled by us when a client asks for it | ~2% + GST domestic; ~3% international | Automatic (webhook) |

> **Original ask** covered Mode A and Mode C. Mode B is the senior-dev recommendation — it removes the manual-confirmation bottleneck while staying at UPI's near-zero cost. See Section 3.

All three modes feed the **same downstream workflow**: once a payment is confirmed (manually or automatically), the invoice/order is marked **Paid**, the customer gets a WhatsApp confirmation, and the ERP/SFA workflow (dispatch, ledger posting, GST records) proceeds as planned.

## 2. Mode A — Manual collection (the baseline, as specified)

### 2.1 Admin panel: payment-details setup
The admin panel must let each merchant configure and store, per business/branch:

- **UPI ID(s)** (VPA, e.g. `business@okhdfcbank`) — with a display name.
- **Static UPI QR code** — either uploaded as an image, *or* auto-generated by us from the UPI ID (preferred — see note below).
- **Bank details** — account holder name, account number, IFSC, bank name, branch. Used for NEFT/RTGS/IMPS.
- **Default collection method** shown to customers.
- **Active/inactive toggle** per method.

> **Build note:** Prefer *generating* the QR from the stored UPI ID rather than accepting an uploaded image. A generated `upi://pay?pa=<vpa>&pn=<name>&cu=INR` QR is always valid, can be made **dynamic** (pre-fill the invoice amount and a note/reference), and avoids the merchant uploading a wrong/expired QR. Keep image-upload as a fallback for merchants who insist on their bank's own QR.

### 2.2 The collection flow (Mode A)
1. Invoice/order is generated in the ERP.
2. System sends the customer a WhatsApp message with the amount, invoice reference, the merchant's UPI QR / UPI ID, and bank details.
3. Customer pays out-of-band (their UPI app or bank transfer). Money lands **directly in the merchant's bank** — we never touch the funds.
4. Customer (optionally) replies "Paid" or uploads a screenshot.
5. **Admin is notified** of a "payment claimed / pending confirmation" against that invoice.
6. Admin verifies against their bank statement / UPI app, then clicks **"Payment Received"**.
7. On confirmation: invoice → **Paid**, ledger entry posted, WhatsApp confirmation sent to customer, downstream workflow triggered.

### 2.3 Why Mode A alone doesn't scale (be honest about this in the UI)
- **Manual reconciliation is error-prone and slow.** The admin has to eyeball each payment against a bank statement. At 10 payments/day it's fine; at 200/day it's a full-time job and a source of disputes.
- **No hard link between payment and invoice.** A customer paying ₹5,000 to a single static UPI ID gives the admin no automatic way to know *which* invoice it was for. This is exactly the pain that virtual UPI IDs (Mode B) solve.

Ship Mode A because it's zero-cost and works on day one — but position Mode B as the natural upgrade the moment volume grows.

## 3. Mode B — Auto-reconciled UPI (recommended addition) ⭐

This is the highest-leverage feature to add. It keeps the merchant's cost at effectively **zero** (UPI MDR is capped at 0% by RBI for transactions up to ₹2,000, and banks — not the merchant — bear the cost) while **eliminating the manual "Payment Received" click entirely**.

### 3.1 How it works
Using a collection product like **RazorpayX Smart Collect** (or the equivalent from Cashfree), the system generates a **unique virtual UPI ID and/or virtual bank account for each invoice or each customer**, linked to the merchant's real bank account.

Example pattern: `rpy.acme<invoiceno>@icici`

Flow:
1. Invoice generated → system creates/assigns a unique virtual UPI ID (or reuses the customer's dedicated one).
2. Customer pays that specific ID via any UPI app.
3. Because the ID is unique, the provider fires a **`virtual_account.credited` webhook** telling us exactly which invoice/customer just got paid, and for how much.
4. System auto-matches, marks invoice **Paid**, sends WhatsApp confirmation, triggers workflow — **no human in the loop.** <cite index="14-1">The merchant receives a real-time alert via dashboard and webhook and the corresponding customer's account is credited automatically.</cite>

<cite index="13-1">Providers report this eliminates manual reconciliation and can save finance teams dozens of hours a month</cite>, and <cite index="11-1">virtual UPI IDs let customers pay directly to the bank account with instant, automated reconciliation.</cite>

### 3.2 Why this belongs in the product
- **Cost:** 0% on UPI (up to ₹2,000/txn), same as Mode A. No gateway MDR.
- **Effort:** Removes the manual-confirmation bottleneck that makes Mode A unscalable.
- **Reconciliation:** Solves the "which invoice was this payment for?" problem structurally.
- **Positioning:** Sits perfectly between free-but-manual (A) and paid-but-full-featured (C). Great upsell.

**Trade-off / prerequisite:** the merchant must onboard a collection account (KYC with the provider). It's not truly zero-integration like Mode A. So keep A as the instant default and offer B as a one-click upgrade.

## 4. Mode C — Full payment gateway (as specified)

Enabled per-client on request. This is the standard hosted-checkout / payment-link experience supporting **UPI + debit/credit cards + net banking + wallets + EMI/BNPL**.

### 4.1 Delivery options (offer all three, pick per context)
1. **Payment link per invoice** — generate a gateway link, send it on WhatsApp. Customer taps → pays → webhook confirms. Zero website needed; fastest to ship. <cite index="27-1">The customer pays in a couple of taps and both parties see confirmation in the same WhatsApp thread.</cite>
2. **Hosted checkout** — for the e-commerce storefront; drop-in checkout script.
3. **WhatsApp-native payment** — see Section 4.3.

### 4.2 Confirmation is always webhook-driven
Never trust the browser redirect. <cite index="19-1">Webhooks are the canonical source of truth — the payment must be handled even if the customer's browser never returns.</cite> Mark the invoice paid only after verifying the webhook signature.

### 4.3 WhatsApp-native payments (important for THIS product)
Because the whole product lives in WhatsApp, support Meta's **India Payments API** so customers pay *without leaving the chat*:

- Merchant links a gateway (Razorpay or PayU) as a **payment configuration** in WhatsApp Business Manager. <cite index="21-1">You configure payment details by selecting the payment type (Razorpay PG, PayU PG, or UPI Intent) and entering the payment ID.</cite>
- To charge, send an **`order_details`** interactive message. <cite index="22-1">Key fields include a unique reference_id (max 35 characters), currency (INR), and total_amount expressed with an offset of 100.</cite>
- <cite index="22-1">Assign the reference_id from your own order-management system — it is the single thread connecting the WhatsApp message, the gateway transaction, the webhook, and the reconciliation record.</cite>
- Drive order state with **`order_status`** messages (pending → processing → shipped → completed / canceled).
- **Gotcha to handle:** <cite index="22-1">cancelling an already-paid order returns error 2047, so fraud/validation screening must happen before sending the order_details message.</cite>
- **Reconciliation caveat:** <cite index="30-1">WhatsApp Pay itself does not do reconciliation — reconcile using the reference_id from the order_details message and the transaction id from the payment-lookup query, against your gateway account.</cite>

> Availability of true in-chat WhatsApp Pay still depends on the BSP and business category; the reliably-available path today is a **gateway payment link sent inside the WhatsApp thread**. Build the link path first, treat native `order_details` as a progressive enhancement.

## 5. Market comparison — which provider(s) to integrate

You don't have to pick one gateway. The pragmatic architecture is **abstract the provider behind an interface** and let us switch/mix per client. Here's the 2026 landscape:

| Provider | Domestic MDR | UPI | Settlement | AMC / setup | Best at | Notes |
|----------|-------------|-----|-----------|-------------|---------|-------|
| **Razorpay** | ~2% + GST | 0% (RBI cap) | T+1/T+2 | ₹0 / ₹0 | Developer experience, ecosystem, WhatsApp integration, Smart Collect | <cite index="4-1">Best all-round default; cleanest API, strong docs, reliable webhooks.</cite> Chargeback ~₹100. |
| **Cashfree** | ~1.75% (headline lowest) | 0% | T+2, **instant (~15 min) at +0.25%** | ~₹4,999/yr AMC | Lowest headline fee, instant settlement, **payouts/marketplace disbursals** | <cite index="1-1">Lower headline rate but charges annual maintenance; cheaper only above a certain monthly volume.</cite> Chargeback ~₹150. |
| **PayU** | ~2–2.5% | 0% | T+2 | varies | **EMI & BNPL (LazyPay)**, enterprise, international | <cite index="7-1">Best EMI tie-ups and BNPL integration; strong for high-ticket (electronics, furniture) where buyers split payments.</cite> Chargeback ~₹200. |
| **PhonePe PG** | ~2% | 0% | — | — | UPI-dominant merchants | <cite index="5-1">Lowest effective cost if >90% of traffic is UPI; weaker on cards/international.</cite> |
| **Instamojo** | — | 0% | — | Zero-cost entry | Solo sellers / no website | <cite index="9-1">Create a payment link in seconds and share on WhatsApp; built for non-technical sellers.</cite> |

### 5.1 The MDR reality (put this in merchant-facing copy)
<cite index="5-1">All the major gateways advertise "0% UPI" because RBI capped UPI MDR. They actually make money on cards (especially international), net-banking commissions, and value-add features (subscriptions, payouts, BNPL) — so don't choose on the headline rate alone.</cite> <cite index="1-1">A 0.1% MDR difference is trivial next to the revenue lost when a gateway fails 5% of UPI transactions</cite>, so **transaction success rate matters more than headline MDR.**

### 5.2 Recommended default stack
- **Primary gateway: Razorpay** — best developer experience, native WhatsApp payments, Smart Collect for Mode B, and it's supported as a WhatsApp payment configuration. <cite index="6-1">For most growing D2C, e-commerce, and SaaS businesses in India in 2026, start with Razorpay; the combination of features, integrations and ecosystem is the best all-round package.</cite>
- **Mode B collection: RazorpayX Smart Collect** (virtual UPI IDs / virtual accounts).
- **Add Cashfree** when a client needs vendor **payouts** or instant settlement. <cite index="5-1">You can layer Cashfree Payouts alongside Razorpay collections — two integrations, no overlap.</cite>
- **Add PayU** only for clients where **EMI/BNPL on big-ticket items** measurably lifts conversion.

Because we serve multiple clients, the provider-abstraction layer (Section 6) is non-negotiable — different clients will want different gateways.

## 6. Architecture

### 6.1 Provider abstraction
Define one internal interface every provider adapter implements. This keeps the ERP unaware of which gateway is in use.

```
PaymentProvider (interface)
  createCollection(invoiceRef, amount, meta) -> { collectionId, upiId?, qr?, link? }
  createOrder(invoiceRef, amount, meta)       -> gatewayOrderId          // Mode C
  verifyWebhook(payload, signature)           -> boolean
  parseWebhookEvent(payload)                   -> NormalizedPaymentEvent
  refund(paymentId, amount)                    -> refundId
  lookupPayment(reference_id)                  -> PaymentStatus
```

Adapters: `ManualAdapter` (Mode A), `SmartCollectAdapter` (Mode B), `RazorpayGatewayAdapter` / `CashfreeAdapter` / `PayUAdapter` (Mode C).

### 6.2 Credential storage (critical — server-side only)
- **Never** ship gateway API secrets, NIC/IRP creds, or merchant bank secrets to the client. Store server-side, encrypted at rest, scoped per-tenant. (Same principle you already applied for the NIC/IRP e-invoice credentials.)
- Webhook signing secrets stored per provider per tenant.
- PCI scope: using hosted checkout / payment links / gateway-tokenised flows keeps card data off our servers entirely. **Do not** build a custom card-capture form.

### 6.3 Multi-tenant note
Each merchant (and possibly each branch) can have its own collection config and its own gateway account. Payment config is a per-tenant setting, not global.

## 7. Data model (minimum viable)

```
payment_method          (id, tenant_id, type[UPI|BANK|QR|GATEWAY], vpa, qr_asset,
                         bank_name, account_no, ifsc, holder_name, is_active, is_default)

payment_config          (id, tenant_id, mode[A|B|C], provider[manual|razorpay|cashfree|payu],
                         provider_account_ref, webhook_secret_ref, enabled_by, enabled_at)

payment                 (id, tenant_id, invoice_id, customer_id, amount, currency,
                         mode, provider, provider_ref, reference_id,      // reference_id = your OMS id
                         status[PENDING|CLAIMED|CONFIRMED|FAILED|REFUNDED|PARTIALLY_REFUNDED],
                         method_used, virtual_upi_id, confirmed_by[system|admin_user_id],
                         confirmed_at, created_at, raw_event_json)

payment_event_log       (id, payment_id, event_type, source[webhook|admin|customer],
                         payload_json, signature_valid, received_at)   // idempotency + audit

refund                  (id, payment_id, amount, provider_ref, status, speed[instant|normal],
                         reason, created_by, created_at)
```

Key constraints:
- `reference_id` is **unique per invoice** and is the join key across WhatsApp message ↔ gateway ↔ webhook ↔ ledger.
- `raw_event_json` and `payment_event_log` give you a full audit trail and enable idempotent webhook processing (dedupe on provider event id).

## 8. Payment lifecycle (state machine)

```
                 ┌─────────── Mode A ───────────┐
 PENDING ──────► CLAIMED (customer says "paid") ──► [admin clicks Received] ──► CONFIRMED
    │                                                                             │
    ├─────────── Mode B/C: webhook (signature-verified) ────────────────────────►┤
    │                                                                             │
    ├────────────────────► FAILED (gateway failure / timeout)                     │
    │                                                                             ▼
    └── CONFIRMED ──► (workflow: mark invoice Paid, post ledger, send WA receipt, dispatch)
                          │
                          └──► REFUNDED / PARTIALLY_REFUNDED (admin-initiated, server-side)
```

Rules:
- A payment can reach **CONFIRMED** only via (a) admin action in Mode A, or (b) a signature-verified webhook in Mode B/C. No other path.
- Confirmation is **idempotent**: re-delivered webhooks must not double-post to the ledger or re-trigger workflow.
- Once CONFIRMED, downstream is identical across all three modes — the rest of the ERP doesn't care how the money arrived.

## 9. Admin panel requirements

### 9.1 Setup screens
- **Collection methods** (Mode A): add/edit UPI IDs, generate/upload QR, add bank accounts, set default, toggle active.
- **Gateway configuration** (Mode B/C): connect provider account, enter/rotate API keys (server-stored), set webhook URL, test with a ₹1 transaction, enable/disable per client.

### 9.2 Operations screens
- **Pending confirmations queue** (Mode A): list of invoices with claimed-but-unconfirmed payments, with the **"Payment Received"** button, customer's screenshot (if any), amount, and invoice link. Bulk-confirm supported.
- **Live payments feed**: real-time list of incoming confirmed payments (Mode B/C) with invoice, amount, method, timestamp.
- **Reconciliation view**: unmatched credits (money received but not auto-matched) surfaced for manual matching.
- **Refunds**: initiate refund (server-side), track status.
- **Notifications**: admin gets a push/WhatsApp/in-app alert on every "payment claimed" (Mode A) and every large / unmatched credit (Mode B/C).

### 9.3 Merchant-facing upgrade prompts
When a Mode-A merchant crosses a volume threshold (e.g. >30 manual confirmations/week), surface a nudge: *"You're spending time confirming payments manually — switch to auto-reconciled UPI (still 0% fees)."* Drives Mode B adoption.

## 10. Security, compliance & edge cases

### 10.1 Must-do
- **Verify every webhook signature** before acting (HMAC-SHA256 with the per-tenant webhook secret). Reject on mismatch.
- **Idempotency:** dedupe on the provider's event/payment id; store processed ids.
- **Amount & currency check:** confirm the webhook amount matches the invoice amount (guard against tampering / partial payments).
- **Refunds are always server-initiated**, never from the customer's device.
- **Credentials server-side, encrypted, per-tenant.** No secrets in the client bundle.
- **Screenshots are not proof** (Mode A): a customer's "paid" screenshot is a *claim*, not confirmation. Admin must verify against the actual bank/UPI record before clicking Received. Consider OCR-assist later, but never auto-confirm on a screenshot.

### 10.2 Edge cases to handle explicitly
- **Underpayment / overpayment:** amount received ≠ invoice amount → route to reconciliation view, don't auto-confirm.
- **Duplicate payment:** same invoice paid twice → flag, offer refund.
- **Late webhook / browser closed mid-payment:** webhook is source of truth; reconcile even if the customer never returned. <cite index="19-1">Always configure the webhook as the source of truth.</cite>
- **Payment-link expiry:** <cite index="28-1">Razorpay payment links expire after 15 minutes by default; for invoice/fee collection set a longer expiry (e.g. 30+ minutes) and auto-regenerate on timeout.</cite>
- **Chargebacks (cards):** you pay a per-dispute fee even if you win — surface these in the admin panel and factor into merchant reporting.
- **Refund timing:** <cite index="19-1">UPI refunds typically reach the customer's bank in 3–5 days</cite> — set customer expectations in the WhatsApp message.
- **Partial shipment / order-status errors:** handle WhatsApp errors 2046 (invalid status transition) and 2047 (cancelling a paid order).

## 11. Open decisions (product owner input needed)

1. **Do we take a cut?** Are we a pure pass-through (merchant's own gateway account, we charge SaaS fee), or do we aggregate payments and take a margin? This changes KYC, escrow, and regulatory scope significantly (aggregation may need a PA/PG licence or a partner who has one). **Recommend pass-through to start.**
2. **Which gateway is the default** we onboard clients with — Razorpay (recommended) — and do we offer a choice at signup or only on request?
3. **Is Mode B in the MVP** or a fast-follow? (Recommend: MVP = A + C-via-link; fast-follow = B + WhatsApp-native.)
4. **Payouts needed?** If clients pay vendors/agents (relevant for SFA), plan a Cashfree Payouts integration.
5. **Subscriptions/recurring?** If any client bills recurring (AMC, subscriptions), plan UPI AutoPay (RBI-approved recurring UPI mandates).

## 12. Suggested build order

1. **Provider abstraction layer** + data model + webhook receiver with signature verification & idempotency.
2. **Mode A**: collection-method setup, QR generation, WhatsApp send, pending-confirmations queue, "Payment Received" button, workflow trigger.
3. **Mode C via payment link**: Razorpay adapter, link generation, WhatsApp send, webhook confirmation, receipts.
4. **Reconciliation + refunds + reporting** (admin panel).
5. **Mode B**: Smart Collect / virtual UPI IDs, auto-match on `virtual_account.credited`.
6. **WhatsApp-native `order_details`** flow as progressive enhancement.
7. **Add-ons per client:** Cashfree Payouts, PayU EMI/BNPL, UPI AutoPay.
